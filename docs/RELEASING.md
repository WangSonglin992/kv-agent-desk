# Windows release builds

The `Windows release` workflow builds on a clean GitHub-hosted Windows runner with Python 3.12. It installs the pinned `requirements-build.lock.txt`, runs the unit suite, and performs both source and packaged-executable smoke tests with `--demo --preview-only --once`. Each uses an isolated directory under `RUNNER_TEMP`; the packaged executable test runs hidden with a 60-second limit, then verifies exit code 0, `frame.png`, and `state.json` with `demo: true`. These checks do not scan agent profiles or access the LCD.

The Windows ZIP is the recommended download. Normal EXE launches install to the current user's fixed application directory, repair the desktop shortcut, and preserve the separate user-data directory; `--portable` skips this installation and automatic updates. To publish a release, push a version tag. The workflow builds `KV-Agent-Desk.exe`, creates `KV-Agent-Desk-windows-x64.zip` with the executable, public notices, CPython license, and text license files exposed by the locked installed distributions, then creates SHA-256 sidecars. It also generates `KV-Agent-Desk.update.json` from the public EXE, its checksum, and the package version. This metadata contains only the exact two executable asset names, sizes, and fixed release URLs. The GitHub Release publishes that manifest with the EXE, ZIP, and checksums. Keep the manifest asset in future stable releases so clients can update without a GitHub login or API quota. Use **Actions → Windows release → Run workflow** to build without publishing; its artifact is retained for 30 days.

The PyInstaller command mirrors `Build-Dashboard.ps1`'s hidden imports and uses an explicit asset allowlist: `app.ico`, `deepseek.png`, `chatgpt.png`, `glm.png`, and `google.png`. The pure-standard-library `tools/package_release.py` writes ZIP entries individually from a fixed public file list and `importlib.metadata` license/copying/notice paths. Neither step packages the assets directory wholesale, `runtime/`, settings, AppData, account data, subscription data, or private logos. The build job has read-only repository permissions and no user-provided secrets. The release job uses the built-in `GITHUB_TOKEN` with `contents: write` only to publish the tag release.

PyInstaller bytecode may contain `co_filename` source paths. In this workflow those paths come from the public GitHub Actions checkout, not a developer's Windows profile or local workspace.
